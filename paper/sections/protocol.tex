\section{Evaluation Protocol}
\label{sec:protocol}

\subsection{Accuracy metrics}
We treat \pd{} as the positive class and report precision, recall and F1 at both operating points, the area under the ROC curve (AUROC) computed from $p_\text{yes}$, and the false-alarm rate (FAR), the fraction of negatives answered ``yes''. FAR is reported for normal frames, for all hard negatives and for each hard-negative subtype, since a pooled figure conceals which postures provoke alarms. We also report recall by camera viewpoint. Confidence intervals are 95\% percentile intervals from a cluster bootstrap that resamples whole source sequences \cite{efron1993bootstrap}, since frames from one sequence are not independent, with 10,000 replicates. When a proportion equals 0 or 1 the percentile bootstrap degenerates to a zero-width interval, so we report the Wilson score interval instead.

\subsection{Efficiency metrics}
For each configuration we measure:
\begin{itemize}
  \item \textit{End-to-end latency}: wall-clock time from sending the request to receiving the last token, measured by the client; it spans image encoding, transfer, vision encoding, prompt processing and decoding.
  \item \textit{Time to first token} (TTFT), measured by the client from a streamed response, plus the server-side prefill and decode times reported by llama.cpp.
  \item \textit{Decode throughput} in tokens per second; with one-word answers, decoding is a minor share of latency.
  \item \textit{Peak memory} (see below), \textit{model size on disk} (language model plus vision projector) and \textit{energy per decision} (see below).
  \item \textit{Streams per device}: the cameras one device can serve at one decision per second each, $\lfloor 1000 / t_{95} \rfloor$ with $t_{95}$ the 95th-percentile end-to-end latency in milliseconds, for sequential processing. We do not batch requests across cameras; batching can raise throughput at the expense of latency and is left to future work.
\end{itemize}

\textit{Measuring memory.} Peak memory is subtler to measure than it appears; in our pilot two common metrics disagreed by more than a factor of three. Resident set size (RSS) counts pages of the memory-mapped weight file once touched; the operating system can evict and reload them, so RSS can overstate what a process truly needs. On Apple Silicon, the ``physical footprint'' metric omits those file-backed pages and also the GPU buffers that wrap them: for the 3\,B model on Metal it reported \PilotLargeGpuFootprintGiB\,GiB, under half the weights' size on disk. On the CPU backend, llama.cpp repacks quantized weights into a CPU-friendly layout and keeps the original mapping, roughly doubling RSS (\PilotLargeCpuRssGiB\,GiB for the 3\,B model with 3.5\,GiB of weights). Table~\ref{tab:memory} separates these effects on the pilot machine. With memory mapping disabled (\texttt{--no-mmap}), weights are copied into private memory and RSS and footprint agree to within 0.06\,GiB in every configuration tried: \AblLargeGpuNoMmapRssGiB\ and \AblLargeGpuNoMmapFpGiB\,GiB for the 3\,B model on the GPU. Disabling repacking (\texttt{--no-repack}) removes the second CPU copy and cuts the 3\,B model's RSS from \AblLargeCpuDefaultRssGiB\ to \AblLargeCpuNoRepackRssGiB\,GiB, at the cost of slower CPU inference. No flag altered a single answer. A system-level measure, the rise in total-minus-available memory over idle, proved irreproducible on macOS: under memory compression and background load it sometimes fell below the process's own private memory. We therefore run all measurements with \texttt{--no-mmap} and report peak RSS, which then equals the memory the model occupies, GPU buffers in unified memory included. Repacking stays enabled, as in deployment, and its cost shows in the CPU figures.

\textit{Measuring power.} We sample macOS \texttt{powermetrics} (CPU and GPU samplers) every 200\,ms. It reports estimated combined CPU, GPU and Neural Engine power, not wall power: memory, display and other components are excluded. Samples carry timestamps of one-second resolution but exact durations, so we build a timeline from the durations and anchor it to the timestamps; over the 65-minute measurement the two clocks diverged by 32\,ms. Each request's start and end are logged, and each power sample is weighted by its overlap with the request windows. Idle power, measured for 60\,s before and after the runs (\PIdleW\,W), is subtracted. Energy per decision is power above idle times request duration, averaged over 60 test frames. Power was measured in a separate run of the Pareto-optimal configurations on the GPU and on the CPU alone.

\subsection{Hardware and software}
We measure on one consumer device, a MacBook Pro with an Apple M4 Pro system-on-chip (Table~\ref{tab:hardware}). Not an embedded board, it serves as two operating points: all computation on the CPU (llama.cpp with the GPU disabled, ten threads on the ten performance cores) as a proxy for CPU-only edge hardware, and all computation on the integrated GPU (Metal) as a proxy for a device with an accelerator. Absolute latencies will differ on embedded hardware. The relative effects of size, precision, resolution and frame count should carry over, as do the device-independent costs we report: weight size, image tokens per decision and model memory. The full grid runs on the integrated GPU; CPU-only runs are confined to the GPU's Pareto-optimal configurations. Because decoding is greedy and deterministic, a configuration yields the same answers on both (Section~\ref{sec:pilot}), so accuracy measured once applies to both.

\subsection{Measurement procedure}
\label{sec:procedure}
Each configuration runs in a fresh server process. We discard three warm-up requests, then time at least 50, reporting the median and 95th percentile. Prompt caching is disabled, so every request processes its image and prompt afresh, as a new camera frame would. Requests are sent one at a time from the same machine. We keep other load minimal, run on mains power and prevent sleep; the last safeguard was added after a pilot run in which macOS entered idle sleep mid-request, which was then logged as taking 1015\,s instead of about 5\,s. During the main grid the machine ran on battery for 41 minutes; we log the power source every minute and re-measured the latency of every configuration whose run overlapped that period. Accuracy is unaffected by power state. Every run records the operating system, runtime build, thread count, power mode and 1-minute load average.
